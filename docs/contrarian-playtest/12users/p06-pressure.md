# P6 后期压力

视角：节奏中等、会漏单会犯错的普通玩家（bot `newbie`：0.9s/步、28% 返工、8% 弃杯；辅以 `regular` 对照）。审查面：第 7-14 天经营压力曲线与经济公平性——首个周租 D7、员工工资与歇业、爆款衰减、连击断档恢复、回暖宽限（goal_relief）的感知度。引擎 Godot 4.6.3，仓库 `/Users/apple/Code/milkteahouse/game`。

复现环境：bot 矩阵 30 组（`BOT_PROFILE/BOT_DAY/BOT_SAMPLE/BOT_STAFF/BOT_STAFF_REST/BOT_UPGRADES/BOT_MENU(_STALE)` 驱动 `tests/autoplay.tscn`，grep `[RESULT]`），覆盖 D7 首租 5 样本+员工在岗 2 组、D9 零升级 5 样本+歇业 2 组、D12-14 零升级/现实升级 8 组、主推热度新旧对比 2 组、regular 对照 5 组；无头 `operating_cost_check.tscn`（`passed ... rent=7d/capped relief=true no_debt=true`）与 `staff_check.tscn`（`passed ... shortfall=9 rest_day=true auto_return=true`）双绿。注：本地存档 `save.json` 为空进度（`day_stars={}`），autoplay `test_mode` 下不写档，样本互不污染；但 `yesterday_stars` 恒为 -1，**bot 无法直接演练 goal_relief 日**，该面结论来自代码全路径追踪 + 数值推算。

## 发现（证据/复现/期望vs实际/修复方向/置信度，S0-S3）

### F1 (S1) 回暖日 3★ 封顶零解释：HUD 悬停说明反向许诺"1.4 倍得 3 星"，结算面板封顶后装作无事发生

- 证据：`game/scenes/day_shop/day_shop.gd:2515-2516` `if goal_relief and stars == 3: stars = 2`（3★ 灵感 +3 同步落空）。但：
  - HUD 目标药丸悬停说明 `_pill_tip(hud_day, "DAY_HUD_GOAL_TIP")`（`:2849`）无条件挂 `ui.csv:822`"今日营收目标：达成得 2 星，**1.4 倍得 3 星**"——回暖日这句是假话；
  - 目标条 `hud_goal_bar` 仍以 140% 满刻度 + 3★ 线渲染（`:2836-2849`），HUD 文本仍显示"3★需%d"（`:2842`），当天 3★ 实际不可得；
  - 结算面板 reward_lines（`:2645-2679`）与全部 `DAY_RESULT_*` 文案键（ui.csv 279-813 逐键核对）没有任何"今日封顶 2★"条目；被顶到 2★ 的玩家看到的是：进度条冲过 3★ 刻度 + 评级章 2★ + 判词"目标达成"，三个信号互相矛盾。
  - 唯一呈现是 `:2845` 徽标 `hud_goal_text.text += " · 回暖日"`——15px、可可色 72% 透明度的文字后缀（`:832-833`），无图标、无专属悬停说明（P12 已报的对比度问题不在此重复，单论信息权重它也不足以承载"今天 3★ 不存在"这种规则变更）。
- 复现（推演路径）：任意 D≤14 战役非合约日拿 0-1★ → 次日 HUD 出现"回暖日"徽标、目标 ×0.85 → 当日营收冲到 ≥1.4×目标（例：D10 基准 260×0.85=221，3★ 线 309）→ 结算 2★、无 +3 灵感、无任何解释。
- 期望 vs 实际：设计注释自述"折价必须透明，玩家不能误判自己的真实实力"（`:2844`），但封顶这个更刺手的半边完全没透明——冲线玩家会以为自己差一点，实际是被规则没收。宽限机制反而在玩家表现最好的那一天失信。
- 修复方向：① 结算面板加一行"回暖日 · 今日封顶 2★"（新 `DAY_RESULT_RELIEF_CAP`，仅在 `goal_relief and earned >= star_goal` 时出现）；② 回暖日悬停说明换变体（"今日宽限：目标 ×0.85，星级封顶 2★"）；③ 目标条当天隐藏/淡化 3★ 线与"3★需"文案。三处至少做 ①②。
- 置信度：高（代码路径完整追踪，文案键全量核对；唯一未做的是带前置存档的真机复现）。

### F2 (S2) 新手第二周营收墙：D9 起 5 样本 4 个 0★、中位怒走 5 人，而目标条每天仍指着不可达的 242-332

- 证据（bot 矩阵，零升级无员工）：
  - D9 五样本：earned 121/186/129/111/161，goal 242，tau 0.50/0.77/0.53/0.46/0.67——4/5 为 0★（<0.7 线）；angry 6/2/5/7/3（中位 5），serve_rate 62-88%（最差 56% 出杯 + 7 人怒走）。
  - D12 三样本 tau 0.56-0.64、D14 三样本 tau 0.58-0.64 全 0★；产出稳定在 166-212 而 goal 曲线 `80+18×day`（`endless_contracts.gd`）爬到 296-332。
  - 同日 regular 对照 tau 1.44-1.69 稳 3★——两档画像之间没有过渡带：要么轻松满星，要么整周 0★。
- 压力来源拆解（代码+数据）：耐心基线 `clamp(34-2×day,16,32)`（`day_shop.gd:1677`）D9 起触底 16s，再叠二遍弯 `×0.96`（`daily_events.gd:133`）≈15.4s；小料 D5+ 恒为 1-2 种（`:1693`）；newbie 每杯 9-12s + 28% 返工（错杯另罚耐心 ×0.65，`:2349`）→ 队首必然超时。错一杯三重罚（原料 + 耐心 + 连击），怒走率雪崩是结构性的。
- 期望 vs 实际：压力本身有兜底（见下），但**连续 0★ 的那一周里，玩家每天盯着一条差 35-45% 的目标条**，判词只有"还在热身，明天再来"（ui.csv:280），夜里提示只有"现有 N 金币 · 研发室可购买店铺升级"（:319）——没有任何"落后 X% / 先买摇茶机"的追赶指引。回暖宽限（次日 ×0.85≈降 36-50 金币）只够把 tau≥0.6 的边缘样本托回 1★ 线（D12 s0 tau 0.63→0.74），对 tau 0.5 档杯水车薪，且玩家要到次日才通过一枚暗色小徽标感知到（见 F1）。
- 但要公平地说：经济没有死循环——净入恒正 72-131/天，D7 周租实付 26-35/40、D14 实付 33-37/60（25% 保护上限生效），每天 dd=1-3 档可买（comfort 60 / tip_jar 70 / shaker 80 一两天攒得出），shaker/smart_sugar 直接压缩步数是正解。墙是"难受但可爬"，不是不公平。
- 修复方向（低成本优先）：0★ 结算日加一句定向提示（"今日营收落后目标 X%——自动摇茶机能把每杯压到 N 次摇茶"之类，指向最能解压的升级）；HUD 目标条连续 0★ 的次日把"3★需"换成"先追 1★ 线"降低视觉压迫。不建议直接削 goal 曲线（regular 档体验会塌）。
- 置信度：高（30 组 bot 数据 + 曲线公式推算）；"难受"的定性部分带主观视角。

### F3 (S2) 周租金额对白天玩家不可见：HUD 只预告"租金D7"天数，40 币的数目最早在扣款当天才出现

- 证据：日间 HUD 成本药丸非租金日显示 `DAY_HUD_COSTS_NEXT`"补货%d · 租金D%d"（`day_shop.gd:2858-2860`，ui.csv:190）——只有天数没有金额、无临近高亮（D5 与 D2 的"租金D7/D7"样式无差别）。金额只存在于两处夜间 UI：结算账本注脚"下次周租 · 第 %d 天 · 基准 %d"（`:2790-2791`）与升级面板预留行"第 %d 天预留 · 工资 %d + 租金 %d · 可安心投入 %d"（`upgrade_panel.gd:116-118`，`upgrade_catalog.gd next_day_reserve`，数值经核对正确：D6 夜→D7 基准 40，D13 夜→D14 基准 60）。租金日当天才切到"租金≤40"（`DAY_HUD_COSTS_TODAY`）。
- 复现：一个不点升级面板的玩家，从 D1 到 D6 白天看到的租金信息全是"租金D7"四个字，D7 打烊才知道要交 40（或被保护到 25%）。
- 期望 vs 实际：首个周租是第二周经济节拍的重大变化（40 ≈ 新手半日净入），期望金额至少提前 1-2 天在日间可见；实际金额只在夜间两个次级面板出现，金币胶囊本体（`hud_coin`）完全不预告。注："≤"措辞对 25% 保护上限是诚实的暗示，这点没问题。
- 修复方向：`DAY_HUD_COSTS_NEXT` 带金额（"租金D7·40"），且距租金日 ≤2 时药丸描边/文字换琥珀色；或金币胶囊悬停说明里加"下次周租：D7 · 40（最多扣现有金币 25%）"。
- 置信度：高（代码+文案定位明确）；严重度中（信息可达但埋得深）。

### F4 (S3) 工资缺口只有事后告知：夜里金币 < 明日工资时无预誓，玩家第一次听说"歇业"是在结算行里

- 证据：工资在日终结算才扣（`day_shop.gd:2519` `charge_daily_wage`），不足→`DAY_RESULT_WAGE_SHORTFALL`"工资实付 %d/%d · 第 %d 天休整"（ui.csv:308）+ 次日员工卡"今日休整 / 少发工资 %d · 今日全部员工效果暂停"（`:1634-1636`）+ 员工面板状态行（ui.csv:388/391）。事前唯一线索是升级面板预留行的"工资 14 + 租金 0 · 可安心投入 0"，但它不会在可投入为负/不足时变红或弹提示。bot 数据侧工资从未真正缺口（最差日净入 72 > 最高日薪 14），`staff_check` 的 shortfall 用例（实付 5/14）走的也是直接构造。
- 期望 vs 实际：歇业一天 = 全部员工效果暂停，是第二周较重的软惩罚；期望"明天发不出工资"在夜里做决定（买不买升级）之前被告知。实际传达链条完整但全在事后。
- 修复方向：`next_day_reserve` 的 investable ≤ 0 且 wage>0 时，升级面板预留行变警示色并补一句"金币不足以支付明日工资——将触发歇业"。
- 置信度：高（流程代码完整核对）；严重度低（触发面窄：日薪 ≤14 vs 最低样本净入 72，正常玩法几乎撞不到）。
